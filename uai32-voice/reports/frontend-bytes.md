# Investigation report: frontend-bytes

Verbatim final report of the investigating agent (2026-10-07). Paths it cites were under the session scratch space; the preserved copies are in this directory tree.

## Summary

I built the audio front-end as one C99 file, vfe.c, in the uai32.c style (one source, no tables, everything from formulas), with two compile-time variants: (a) FE_BIQUAD, 16 RBJ second-order band-pass biquads (transposed DF2) on mel-spaced centres with bandwidth = half the neighbour spacing, no FFT; (b) FE_FFT, a 256-point radix-2 complex FFT on real input with a sin^2 (Hann) window computed at start-up and 16 triangular mel filters evaluated bin-by-bin from 18 band edges (100-7000 Hz). Both use 16 ms frames / 8 ms hop (124 frames per 1 s window), floor the band energies at 1e-7 (full-scale sine = 1.0), take logs, and pool the 124 frames into 12 segments by averaging log energies, giving 192 features; -n optionally subtracts each band's mean over time; input is raw 16 kHz 16-bit LE mono PCM or WAV (chunk-walked, fmt checked) from a file or stdin, zero-padded/truncated to 1 s, output is one uai32 data row with an optional trailing label. I compiled each variant standalone and merged (by merge.sh) into a copy of uai32.c as a new verb `uai32 feat`, with EXACTLY the Makefile CFLAGS/LDFLAGS including -Wl,-z,nosectionheader, after first reproducing the 9,188-byte baseline byte-identically with the same toolchain (gcc 13.3.0, binutils 2.42, glibc 2.39). Measured merged executables: biquad 10,892 bytes (+1,704), FFT 11,412 bytes (+2,224), FFT with cos written as a shifted sinf 11,340 bytes (+2,152); the only libm symbols added are sinf (biquad) and sinf+sincosf (FFT; gcc fuses the cosf/sinf pair), and each extra import costs about 65-80 bytes of .dynsym/.dynstr/.rela.dyn/.got/version tables, the rest of the delta being .text (+1,446 / +1,894) and .rodata (+176, strings and float constants). The -n code costs 128 (biquad) / 144 (FFT) bytes; changing NB/NT moves the size by at most 48 bytes. An important layout finding: with the buffers as static arrays (.bss 40-45 KB) the executables were 96-192 bytes smaller (10,796 / 11,220) but GNU ld then started the RW segment on a fresh page for some .bss sizes, adding 1,752-2,168 bytes of zero padding with identical sections (observed at NB=12), so I switched to one calloc (40,776 B biquad / 44,872 B FFT, .bss 200-240 B), after which no configuration showed padding; the standalone numbers (4,688 biquad incl. 316 B of such padding, 4,896 FFT) are less meaningful than the merged ones. Correctness: 188 checks pass against a float64 numpy reference of the same formulas (max |difference| 0.0005, i.e. the 3-decimal print resolution, both above and near the floor), silence gives exactly ln(1e-7) = -16.118 in all 192 features, tones at each of the 16 band centres light exactly that band in both variants (biquad peak -1.387..-1.384 vs the exact ln(A^2) = -1.386; FFT -1.30..-1.02 because the Hann main lobe spreads over 2-3 bins), 440/1000/3000 Hz tones land in the analytically predicted band, an onset at 0.55 s leaves segments 0-5 at the floor and 7-11 steady, WAV/raw/stdin/extra-chunk give identical rows, wrong formats are refused, and a 4-class synthetic end-to-end run through the merged binaries (feat -> train -> test) scores 40/40 (FFT) and 39/40 (biquad) with a 7,856-byte 192-16-4 model. Speed: 1.0-1.6 ms (biquad) and 1.15-1.45 ms (FFT) per second of audio in-process at -Os on a 2.8 GHz Xeon; a whole process run including start-up is 3.5-4.8 ms; peak RSS 11.2 MB, the same as the baseline uai32 (glibc dominated). Budget: with model bytes = 8 + 8*NI + 2*(NH*(NI+1) + NO*(NH+1)), the FFT executable leaves 32,768 - 2,000 - 11,412 = 19,356 bytes for the model, so at NI = 192 and NO = 6 the largest hidden layer is NH = 44 (model 19,068, total 30,480, spare 2,288; NH = 48 would be 20,660 and total 32,072, spare only 696), and with the biquad executable NH = 46 (19,864; total 30,756; spare 2,012); NI = 160 allows NH = 54-56, NI = 128 allows NH = 67-70. The FFT/mel bank is far more selective (neighbouring bands 10-13 nats down versus 1.4-2 nats for second-order biquads) for only 448-520 more bytes, so it should be the primary front-end. Not covered by these bytes: utterance alignment inside the fixed 1 s window and a rejection threshold, which the host can apply to the probabilities predict already prints.

## Recommendation

Use the FFT/mel front-end (256-point radix-2 FFT, sin^2 window, 16 triangular mel bands 100-7000 Hz, 16 ms / 8 ms framing, mean-of-log pooling into 12 segments = 192 inputs) merged into uai32 as the `feat` verb: it costs 2,224 bytes (11,412-byte executable; 2,152 with cos written as a shifted sinf) versus 1,704 for the biquad bank, and the 448-520 extra bytes buy 10-13 nats of neighbour-band rejection instead of 1.4-2.0, which matters for similar-sounding words. Keep every buffer in one calloc (as uai32 does), never in static arrays: with a 40 KB .bss GNU ld can start the RW segment on a new page and silently add up to 4,095 bytes of zero padding to the file (observed +1,752/+2,168), and check `readelf -l` on every budgeted build that the RW offset equals the end of the RX segment. Declare the class capacity up front (uai32 fixes NO at creation): NO = 6 covers three enrolled commands, the fourth added after restart, and spare/garbage classes. With NI = 192 and NO = 6 the budget allows NH <= 44 (FFT) or 46 (biquad) with >= 2,000 bytes spare; a smaller NH (24-32, model 11,100-14,300 bytes) is plenty for 3-4 commands from 5 examples each and leaves 7-10 KB for an onset/alignment step and a rejection rule, so I would budget NH = 32 and keep NH = 44 as the ceiling. If bytes get tight, drop to NI = 160 (10 segments) before touching the FFT. Protocol: enrol with `uai32 feat -n cmd_i_k.wav i >> train.txt` then `uai32 train train.txt cmd.model 32 EPOCHS RATE SEED`; recognise with `uai32 feat -n x.wav | uai32 predict cmd.model`, applying a max-probability threshold (fixed before testing) on the printed probabilities, host-side or as a few bytes in predict; continuing training after restart is already supported by uai32's `train` on an existing model file. Report the executable, the model file at the declared capacity, and `readelf -l` evidence of no padding, as the byte accounting.

## Risks

- Fixed 1 s window with no utterance alignment: real recordings differ in onset, so the MLP must learn time-shift invariance from 5 examples; an energy-based onset trim or centring (host-side or a few hundred bytes more) is not included in the measured 1,704/2,224 bytes and is probably the largest accuracy risk.
- All correctness evidence is on synthetic signals (tones, noise, synthetic tone classes); recognition accuracy on speech, speaker variation and the 1% false-accept target are untested here, and the biquad end-to-end run already lost 1 of 40 on an easy synthetic task.
- Rejection of unfamiliar speech needs a probability threshold or a garbage class; neither is in the measured bytes (a host-side threshold on predict's printed probabilities costs 0 executable bytes, an in-binary one was not measured).
- Executable size depends on linker layout, not only on code: static buffers caused +1,752/+2,168 bytes of page padding at some .bss sizes; any future change of buffer sizes or compiler/binutils version must be re-checked with readelf -l.
- The 192-44-6 ceiling is ~8,800 weights trained from 15-20 examples: heavy overparameterisation; expect to need gain/time-shift augmentation or a smaller hidden layer, and an untrained and shuffled-label control as the challenge requires.
- Second-order biquads leak strongly into neighbouring bands (only 1.4-2 nats down) and their absolute level is transient-dependent in the first frames; if chosen for bytes, expect weaker discrimination of similar-sounding words.
- The FFT variant's absolute tone level varies by up to 0.3 nat (2.5 dB) with the tone's position relative to the FFT bins; harmless after training but visible in raw features.
- Timings are from one 2.8 GHz Xeon container with 30% run-to-run variance; the per-second cost (about 1.1-1.4 ms) is small enough that this does not matter on a desktop.
- sincosf is a gcc-generated import (cosf+sinf of the same argument under -fno-math-errno); another compiler may import cosf and sinf instead (still two imports, same order of bytes), and sinf results from a different libm could change low bits of the features but not the accuracy.
- WAV parsing reads samples up to 1 s or EOF without honouring the data-chunk length, so a WAV with chunks after `data` and under 1 s of audio would mix chunk bytes into the tail of the signal (documented, not expected in practice).
